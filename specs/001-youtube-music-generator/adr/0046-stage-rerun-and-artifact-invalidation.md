# ADR-0046: 工程単位のやり直しと、成果物依存 DAG による無効化規則

- **ステータス:** Accepted
- **日付:** 2026-07-25
- **決定者:** @seita
- **タグ:** backend / frontend / policy

## 背景

枠詳細から「この工程からやり直す」を提供するにあたり、当初は「やり直した工程より**下流の工程**の成果物を破棄する」という工程順序ベースの規則を考えていた。しかしこの規則は次の 2 つの操作を表現できない。

- **トラック単体の再生成**: 6 本のうち 1 本だけ作り直す。工程としては「音楽生成」の一部でしかないが、**検査と動画合成は必ずやり直す必要がある**。ここを見落とすと未検査の音源が公開される
- **文言だけのやり直し**: タイトル・説明文だけ作り直し、動画とサムネは保持する。工程としては「パッケージング」の一部だが、下流に影響しない

つまり無効化の単位は工程ではなく**成果物**であり、順序ではなく**依存関係**で決まる。

## 決定

### (1) 成果物と依存 DAG

枠が持つ成果物と、その依存関係を次のとおり定義する。

```text
plan(企画JSON)
 ├→ track[1..6](音源)
 ├→ thumbnail(サムネ)
 ├→ title
 └→ description

track[1..6]
 ├→ inspection(指紋・音量・尺の検査結果)
 ├→ mix(6本連結した音声)
 └→ chapters(チャプター)

mix + thumbnail → video(合成済み動画)

video + title + description + inspection → package(公開可能な一式)
```

各成果物はバージョンを持ち、「どの入力(プロンプト版・モデル・上流成果物の版)から作られたか」を記録する。

### (2) 無効化規則

> **成果物 X を再生成すると、X に推移的に依存する成果物はすべて無効化される。X に依存しない成果物は保持される。**

適用例:

| 操作 | 再生成 | 無効化(作り直し) | 保持 |
|---|---|---|---|
| 企画からやり直す | `plan` | すべて | なし |
| 音楽生成からやり直す | `track[1..6]` | `inspection` / `mix` / `chapters` / `video` / `package` | `plan` / `thumbnail` / `title` / `description` |
| **トラック 03 だけ再生成** | `track[3]` | `inspection` / `mix` / `chapters` / `video` / `package` | 他 5 トラック / `plan` / `thumbnail` / `title` / `description` |
| パッケージングからやり直す | `thumbnail` / `title` / `description` | `video` / `package` | `plan` / `track[*]` / `inspection` / `mix` / `chapters` |
| **文言だけやり直す** | `title` / `description` | `package` | 上記以外すべて(`video` / `thumbnail` を含む) |
| 再検査 | `inspection` | `package` | 音源・動画・文言すべて |

これにより、**トラックを差し替えたら検査と動画合成が必ず走る**ことが規則から導かれる。個別に「トラック再生成のときは再検査する」と書く必要はない。

### (3) 承認の失効

> **無効化された成果物を持つ枠は `awaiting_approval` / `approved` / `published` を取れない(ADR-0045 INV-5)。**

`approved` の枠でやり直しを行うと、枠は `in_production` に戻り(T17)、**承認は失効する**。再度パッケージングまで完了したら、あらためて公開ゲートを通る。承認済みの動画をこっそり差し替える経路は存在しない。

`published` の枠に対するやり直しは提供しない(公開済み動画の差し替えは行わない)。作り直したい場合は取り下げ(ADR-0043)+ 単発枠の追加とする。

### (4) プロンプトを修正してからのやり直し

企画(planner)とパッケージング(finisher / title / description)は、**プロンプトを修正してからその枠だけ再実行**できる。

- 修正したプロンプトは新バージョンとして保存され、既定として以後の枠にも適用される(プロンプトのバージョン管理は既存方針を継承)
- **この枠だけに適用して試す**場合は、枠にプロンプト版のオーバーライドを記録する。どの版で作られたかは成果物に残る((1))
- どちらの場合も、再実行は (2) の無効化規則に従う

### (5) やり直しの記録

やり直しは監査ログではなく**枠のタイムライン**に記録する(誰が / いつ / どの成果物を / なぜ)。旧世代の成果物は即座には消さず、保持期間(ADR-0049)を置いてから削除する。

## 結果

### 良い影響

- 「未検査の音源が公開される」経路が規則レベルで閉じる
- 部分やり直し(トラック 1 本・文言だけ)を安全に提供でき、GPU 時間と待ち時間を節約できる
- 「この操作で何が消えるか」を DAG から機械的に導けるため、UI の確認文言を生成できる

### 悪い影響・トレードオフ

- 成果物ごとのバージョンと依存の記録が必要になり、データモデルが旧設計より複雑になる
- 承認失効の規則により、「承認後にちょっとだけタイトルを直す」ができない(再承認が必要)。安全側として受容する

### 受容したリスク

- DAG の定義がコードと ADR で二重管理になり、乖離しうる。DAG はコード上で単一定義とし、無効化は必ずその定義から導出する(手書きの分岐を書かない)

## 検討した代替案

- **工程順序による下流破棄:** トラック単体再生成と文言だけやり直しを表現できない。不採用(本 ADR の背景)
- **やり直しは常に全部作り直し:** 安全だが GPU 時間が無駄になり、「文言だけ直したい」に 40 分かかる。不採用
- **承認を維持したまま成果物を差し替える:** 公開ゲートを通っていない成果物が公開される。不採用
