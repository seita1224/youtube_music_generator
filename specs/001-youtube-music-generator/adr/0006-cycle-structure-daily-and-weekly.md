# ADR-0006: サイクル構造 = 日次サイクル + 週次サイクル の2層

- **ステータス:** Accepted
- **日付:** 2026-05-25 (改訂: 2026-07-11 — 音楽専用実行モードを追加)
- **決定者:** @seita
- **タグ:** backend, ops

## 背景

当初要件は「1サイクル = 1日1回」とした上で、同じサイクル内に「1週間待機 → 分析 → 改善計画」が含まれていた。
これは構造矛盾(日次 vs 週次の混在)で、実装時に必ず手戻りする(グリル Q8)。

段階導入では、まず承認済み Daily Plan から **音楽生成だけ** を完了させ、AcoustID・画像・動画・YouTube 投稿は後段に残す必要がある。
フル日次パイプラインと音楽専用経路を同一オーケストレータに押し込むと、不要な外部依存(AcoustID / OAuth / Slack)が起動時に要求され、進捗の完了条件も曖昧になる。

## 決定

サイクルを **明示的に2層に分離** する。加えて、日次側に **音楽専用実行モード** を独立定義する。

### 日次サイクル(フルパイプライン、将来の投稿完了経路)

入力: 改善計画 v_n(週次サイクルが書き出した最新版)と、承認済み Daily Plan
処理:

1. ジャンル選定(マスターLLM・改善計画 v_n のプロンプトに従う) — Plan 承認済みなら Plan.payload を正とする
2. 楽曲生成(ACE-Step、ジャンル内 6 サブテーマで 5分 × 6本)
3. AcoustID プレチェック → NG なら再生成 or スキップ
4. 楽曲連結(ffmpeg `acrossfade`)
5. サムネ画像生成(SDXL)
6. 動画合成(ffmpeg、波形ビジュアライザ + サムネ + 音声)
7. タイトル・説明文生成(マスターLLM、ディレクティブ展開)
8. YouTube 投稿(または dryrun ならスキップ、ADR-0007)
9. 失敗は Slack 通知のみ、ジャンル単位で独立(1ジャンルが落ちても他は継続)

出力: 投稿動画メタデータ・生成ログ → DB

### 音楽専用実行モード(現行の即時・定時実行の正)

フル日次のうち **Post 作成 → MusicJobRunner → AudioTrack / WAV 確定** までを独立ジョブ `music_generation` として実行する。

- **入力:** `status=approved` の Daily Plan のみ。未承認・実行中・完了済み Plan は起動しない
- **処理:** Plan の各 Post について 6 トラックの音声を生成し、`audio_tracks` とストレージ上の WAV を確定する
- **非実行:** AcoustID、画像生成、ffmpeg 連結/動画合成、YouTube 投稿、Slack 必須通知。`fpcalc` / AcoustID key / YouTube OAuth / Slack webhook は本モードの前提にしない
- **状態遷移:**
  - Plan: `approved → executing → music_generated | failed`
  - Post: `pending → generating → music_generated | failed`
- **成功条件:** 対象 Plan の各 Post で AudioTrack 6 件と WAV が揃った時点。動画・投稿は不要
- **トリガ:** 管理UI の即時実行(`run_now`)と APScheduler 定時実行(`cron`)は同一サービスを共有する(ADR-0011)

出力: Post / AudioTrack メタ・WAV・実行履歴(`job_history` / `job_step_events`) → DB + storage

### 週次サイクル(週 1 回起動、初期は固定曜日)

入力: 過去 7 日分の投稿動画の視聴数・コメント・retention・watch time
処理:

1. ジャンル別パフォーマンス分析(マスターLLM)
2. コメントの傾向分析(マスターLLM)
3. 改善計画 v_(n+1) の生成(ジャンル選定方針・プロンプト・説明文テンプレ等への反映)
4. 人間レビュー枠(管理UI 上で承認すれば反映、放置なら自動反映するかは設定で切替)

出力: 改善計画 v_(n+1) → DB → 翌日以降の日次 / 音楽専用実行が参照

## 結果

### 良い影響

- 実装責務が綺麗に分離(日次バッチ / 週次バッチが独立ジョブ)
- 音楽専用モードにより、外部 API キー無しでも承認 Plan → 再生可能な音声まで検証できる
- 改善計画のバージョン管理が明確、ロールバック可能
- 人間レビュー枠を挟む選択肢が自然に入る

### 悪い影響・トレードオフ

- 2ジョブのスケジューラ設定が必要(cron / APScheduler / 自前スケジューラ)
- フル日次と音楽専用で状態(`music_generated` vs `completed` / `posted`)が分岐する
  - 緩和: `music_generated` を明示 enum とし、後段パイプラインは別ジョブとして接続する
- 改善計画の整合性チェック(壊れた計画で日次が暴走しないか)が必要
  - 緩和: 実行開始時に改善計画 / Daily Plan の schema 検証。未承認 Plan は起動拒否

### 受容したリスク

- 改善計画 v_n がバグっていた場合、人間レビュー枠を通さない設定では翌日の投稿が全滅する可能性
  - 対策: dryrun モード(ADR-0007)でレビュー可能に。現行は承認済み Plan のみ実行

## 検討した代替案

- **当初要件通り1サイクル:** 構造矛盾、実装時に手戻り。不採用。
- **改善を日次に組み込む:** 1日のデータでは統計的に意味がない。不採用。
- **週次の代わりに月次:** 立ち上がり期のフィードバックが遅すぎる。不採用。
- **フル日次を stop_after フラグで途中停止:** 依存組み立てと完了条件が曖昧。音楽専用オーケストレータを分離する方が明確。不採用。
