# ADR-0026: バックアップ = ローカル別ディスクのみ(段階的アプローチ)

- **ステータス:** Accepted
- **日付:** 2026-05-25
- **決定者:** @seita
- **タグ:** ops, infra, security

## 背景

ADR-0010(PostgreSQL)・ADR-0012(OAuth 暗号化)・ADR-0022(fsspec ストレージ)で発生する永続データのバックアップ運用を決める。

対象:

- PostgreSQL ダンプ(状態・履歴・改善計画・usage_log・OAuth トークン[暗号化済み])
- 楽曲ファイル(永続、年 60〜200GB)
- サムネ画像(年 数GB)
- OAuth Fernet 暗号鍵(`.env`、別管理が原則)

クラウドバックアップは検討したが、当面はコスト・運用負荷を抑え **ローカル別ディスクのみ** で開始。将来規模拡大時にクラウド追加を検討。

## 決定

### バックアップ先

- **ローカル別物理ディスク**(GPU マシンに増設、または NAS)
- マウント例: `/mnt/backup`
- DB ダンプとストレージファイルは別ディレクトリで管理

### ツール

- DB ダンプ: **`pg_dump`**(ロジカルダンプ、圧縮 `-Fc`)
- ファイル同期: **`rsync`**(楽曲・サムネ等の差分同期)
- スケジュール: APScheduler(ADR-0011)の別ジョブとして登録

### スケジュールと retention

```text
DB ダンプ:
  日次:  毎日 1 回(深夜)、過去 7 世代を保持
  週次:  日曜 1 回、過去 4 世代を保持
  月次:  毎月 1 日、過去 12 世代を保持

ファイル同期(rsync):
  日次:  毎日 1 回、増分同期(削除は伝播させない、--update)
  月次:  完全同期 + 旧ファイルクリーンアップ
```

### Fernet 暗号鍵(`.env`)の別管理

- DB ダンプと **同じディスクには置かない**(ダンプを盗まれても復号不能の前提を維持)
- 推奨保管先(いずれか):
  - パスワードマネージャ(1Password / Bitwarden)
  - 物理 USB / 別 PC のディスク
  - クラウド鍵管理(将来導入なら GCP KMS / AWS KMS 等)
- 年次でローテーション(ADR-0012)

### 復旧テスト

- 四半期に 1 回、別ディレクトリへの復元テスト(`pg_restore` + ファイル展開)
- 管理UI から復旧 dryrun コマンドを叩ける形が理想(Phase 2)

## 結果

### 良い影響

- 運用シンプル、外部依存ゼロ
- ディスク故障単体での復旧が可能
- クラウド月額コストが発生しない

### 悪い影響・トレードオフ

- **マシン全損(火災・盗難・電源障害でディスク両方故障)で全データ喪失**
  - 影響: 楽曲アセット・OAuth トークン・改善計画履歴・analytics 蓄積が消える
  - 復旧経路: YouTube 側の投稿動画(別の Google アカウントで OAuth 再認可で取り戻し可能)、楽曲アセットは再生成、改善計画履歴・分析データは失われる
- 別ディスクの増設・マウント設定が必要

### 受容したリスク

- マシン全損時に全データ喪失することを **明示的に受容**
  - 動機 B(観察データ蓄積)が部分的に毀損する可能性があるが、現時点では運用シンプルさを優先
- 将来規模拡大・収益化が進んだ時点でクラウドバックアップ(ADR 後継)を再検討

## 検討した代替案

- **ローカル別ディスク + クラウド(B2/R2)+ restic:** 全損耐性が高く重複排除・暗号化も標準装備、月コスト $1〜10。運用負荷増を許容できれば理想だが、当面は採用見送り。将来検討。
- **クラウドのみ(restic + B2):** マシン全損耐性 ◎ だが、ローカル高速復元不可、クラウド依存。不採用。
- **バックアップなし:** リスク許容度を超える。不採用。
