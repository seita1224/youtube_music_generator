# ADR-0041: 公開枠(Slot)を集約ルートとする再設計

- **ステータス:** Accepted
- **日付:** 2026-07-25
- **決定者:** @seita
- **タグ:** backend / frontend / ops / policy

## 背景

旧設計は 1 本の動画を作るまでに DailyPlan / WeeklyPlan / dryrun_output / Post / job_history という 5 つの状態機械を横断する。どれが主で、どれが従かが定義されていないため、次の問題が同時に起きていた。

- 承認ポイントが分散する(ADR-0042 で定量化)
- 「今この動画はどの工程にいるのか」を 1 画面で答えられない
- 画面が概念(Plan / dryrun / Post)ごとに割れ、ユーザーが日常的に見たい「いつ何が公開されるか」に対応する画面が無い

一方でユーザーの実際の運用単位は「月曜 07:00 に Lo-Fi を 1 本出す」という**投稿の枠**であり、Plan でも Post でもない。

## 決定

### (1) 枠 = 集約ルート

**公開枠(Slot)= 公開日時(JST)× ジャンル指定** を集約ルートとし、制作に関わる全成果物は枠に属する。DailyPlan / dryrun_output / Post は独立した集約としては持たず、枠配下の成果物(ADR-0046)と枠の状態(ADR-0045)に統合する。

各枠は自分の制作ラインを 1 本持つ:

```text
企画 → 音楽生成 → 検査 → パッケージング → 公開待ち → 公開 / 見送り
```

### (2) 公開枠パターンと物化

ユーザーが編集するのは**枠行のリスト(公開枠パターン)**だけとする。枠行 = 曜日 × 時刻(JST)× ジャンル指定。

- パターンはバージョン管理する。変更は **`empty` 状態(制作未着手)の将来枠にのみ**反映し、制作が始まった枠と過去枠は変更しない
- 単発の変更(この日だけ休む / この日だけジャンルを変える / 臨時に 1 本足す)はパターンを変えず、**枠個別の例外**として持つ
- **物化(materialize)**: 毎日 03:00 JST に、その時点のパターン + 例外から翌日分の枠を生成する。物化は同一入力に対し決定論的でなければならない(Lean 形式化対象)
- **枠 ID は物化時に採番し、以後変わらない**。パターンを編集しても既存枠の ID は維持される。パターン行の削除は、未着手の将来枠の削除として反映する

### (3) ジャンル指定の 3 種

| 指定 | 意味 |
|---|---|
| 固定 | 具体ジャンル名を直接指定 |
| おまかせ | 物化時に AI がジャンル配分と直近実績から選ぶ。**role が主力 / 拡張のジャンルのみ**を対象とし、実験ジャンルは選ばない |
| 実験 | role = 実験 のジャンルを**ユーザーが明示指定したときだけ**編成に出る |

おまかせの選択基準は ADR-0047 の目的関数に従い、選択理由を枠詳細に表示する。

### (4) 投稿本数は枠数で表現する

「1 日 N 本まで」という上限をシステムに持たせない。枠を増やせばその分の制作ラインが走る。実効上限は次の 2 つの外部制約としてのみ現れる:

- YouTube API quota による 1 日の公開本数(ADR-0045)
- GPU 1 台の直列処理能力

**GPU 実行順は公開予定時刻の早い順(EDF)**とする。同時刻なら物化順。締切に間に合わない枠が発生した場合、枠は `failed` ではなく通常どおり制作を続け、完成後に遅延公開(ADR-0045)として扱う。

### (5) 画面構成

一覧 → 詳細のブレイクダウンを基本構造とする。

| 画面 | 役割 |
|---|---|
| **編成表**(ホーム) | 週間カレンダー。枠の色 = 制作ラインの現在地。公開枠パターンの編集もここ |
| **枠詳細**(ドリルダウン) | 枠 1 つの工程詳細。各工程の「使った(入力)/ できた(出力)」+ 工程単位のやり直し(ADR-0046)+ 公開ゲート(ADR-0042) |
| タイムライン | 出来事ログ + 当日サマリ |
| ジャンル | ポートフォリオと role 遷移 |
| 分析 | KPI と企画へのフィードバック |
| プロンプト | 工程 1:1 のプロンプト管理 |
| 設定 | 自動運転レベル / LLM / GPU / バックアップ |

旧画面のうち、全ジョブ横断の制作ラインボード・受信箱・公開キュー・運営方針は廃止する。「どのジョブがどの工程にいるか」の横断ビューは編成表の色で代替し、工程の詳細は枠詳細に集約する。

## 結果

### 良い影響

- ユーザーの運用単位(枠)とシステムの集約単位が一致し、「いつ何が出るか」が 1 画面で答えられる
- 状態機械が枠 1 本に集約され、ADR-0045 で全状態を閉じた形で列挙できる
- 投稿本数の増減がパターン編集だけで完結する(旧 ADR-0004 の段階拡大は枠数の問題に還元される)

### 悪い影響・トレードオフ

- 旧 DailyPlan / dryrun_output / Post を前提としたテーブル・API・画面は作り直しになる(ADR-0050)
- 「1 本の動画に対する複数案の比較」のような、枠に紐づかない探索的な生成は表現できない。プロンプト画面の「試しに 1 件生成」(枠に影響しない実行)で代替する

### 受容したリスク

- パターン変更が将来枠にしか効かないため、「今日の枠のジャンルを変えたい」は例外操作という別経路になる。操作が 2 系統に分かれる分かりにくさは残る

## 検討した代替案

- **Plan を集約ルートに残す:** 現行構造の延長。ユーザーが見たい「枠」と一致せず、再設計の動機を解決しない。不採用
- **枠を持たず、完成した動画をキューに積んで順に公開する:** 公開日時がジャンル配分から切り離せず、「月曜は Lo-Fi」のような編成が組めない。不採用
- **1 日 N 本の上限をシステム設定で持つ:** quota と GPU という実制約が別にあるのに、それと独立した上限が増えるだけ。不採用
