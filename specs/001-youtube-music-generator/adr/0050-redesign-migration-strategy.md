# ADR-0050: 再設計の移行戦略(作り直し + 工程実装の移植)

- **ステータス:** Accepted
- **日付:** 2026-07-25
- **決定者:** @seita
- **タグ:** backend / frontend / ops

## 背景

ADR-0041〜0049 は、集約ルート・承認モデル・状態機械・画面構成を作り替える。既存実装をどこまで活かすかを決めないと、着手できない。

既存実装の構造を見ると、再設計が触る領域と触らない領域がはっきり分かれている。

- **触る領域**: DailyPlan / WeeklyPlan / dryrun / Post の各状態機械、承認 API、スケジューラの起動条件、管理 UI 全画面
- **触らない領域**: ACE-Step の呼び出し、指紋検査、音量正規化、ffmpeg 合成、サムネ生成、YouTube クライアント、鍵管理、LLM プロバイダ抽象

承認過多も概念の分散も、前者(オーケストレーション層)に埋まっている。

## 決定

### (1) オーケストレーション層は新規実装する

枠・パターン・物化・状態機械・スケジューリング・承認・管理 UI は**すべて新規に書く**。既存の Plan / dryrun / Post 系のテーブル・API・画面を改修する形は取らない。

理由: 旧概念(Plan・dryrun・モード切替)がデータモデルと API 名に埋め込まれており、改修では概念が残る。ADR-0041 の集約ルート変更は、実質的にこの層の書き直しである。

### (2) 工程実装は旧リポジトリから移植する

次は動作実績があり、再設計と独立しているため、コードを移植して再利用する。

| 対象 | 出典 ADR |
|---|---|
| ACE-Step 1.5 呼び出し / GPU worker との HTTP 契約 | ADR-0031 |
| AcoustID + Chromaprint 指紋検査 | ADR-0005 |
| 音量正規化・尺・無音率の自動検査 | ADR-0039 |
| ffmpeg 動画合成(showwaves overlay) | ADR-0015 |
| サムネ生成(Juggernaut XL v10) | ADR-0016 |
| YouTube クライアント(投稿・`containsSyntheticMedia`・Analytics 取得) | ADR-0020、ADR-0021 |
| OAuth トークンの Fernet 暗号化 | ADR-0012 |
| LLM プロバイダ抽象 / 構造化出力 / コスト記録 | ADR-0018、ADR-0019、ADR-0024 |
| 認証(セッション BFF) | ADR-0013 |
| directive parser、デフォルトテンプレ | ADR-0017、ADR-0034 |

### (3) データ移行

- 旧 DB から引き継ぐのは、**公開済み動画の実績データのみ**(video_id・公開日時・ジャンル・Analytics)。ADR-0047 の目的関数が過去実績を必要とするため
- Plan / dryrun / job_history / 未公開の生成物は引き継がない
- 移行は 1 回きりのスクリプトとし、恒久的な互換層は作らない
- 旧リポジトリは**参照用に凍結**する(削除しない)

### (4) 認証は継承する

管理 UI の認証(ADR-0013 のセッション認証 BFF)を継承する。単一ユーザー・パスワードのみ、2FA なし。**LAN 内でも認証は必須**とする(将来のトンネル公開および他端末からの誤操作への備え)。画面モックには認証画面を含めない(モック対象外)。

### (5) 旧 ADR の扱い

**置き換えられる ADR**

| 旧 | 置き換え先 |

## 結果

### 良い影響

- 再設計の動機(承認過多・工程の不可視)を、旧概念を引きずらずに解消できる
- 動作実績のある工程実装を捨てないため、リスクの高い部分(GPU・外部 API)を再検証せずに済む

### 悪い影響・トレードオフ

- 実装量は改修より大きい。管理 UI は全画面が新規になる
- 移行期間中は旧システムを止めることになる(並行稼働はしない)。個人運用のため許容する

### 受容したリスク

- 「触らない領域」と判断した工程実装が、実際には旧オーケストレーションに依存している可能性がある。移植時に判明したら個別に切り出す
- 旧 DB の実績データが少なければ、ADR-0047 の判断は当面サンプル不足で動かない(閾値により自動判断が保留されるだけで、破綻はしない)

## 検討した代替案

- **既存実装を段階的に改修する:** 旧概念がデータモデルに残り、再設計の目的を達しない。不採用
- **全部ゼロから作る(工程実装も含む):** GPU・外部 API 周りの再検証コストが高く、得るものが無い。不採用
- **旧 DB を全面移行する:** 引き継ぐ先の概念が無い(Plan / dryrun)。実績のみに限定
