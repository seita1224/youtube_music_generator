# ADR-0007: dryrun モードを MVP 必須機能に含める

- **ステータス:** Accepted
- **日付:** 2026-05-25
- **決定者:** @seita
- **タグ:** backend, frontend, ops

## 背景

要件「開発と本番を分けず同一マシンで運用」は、1人運用前提では合理的な簡素化だが、グリル(Q後半)で以下が問題化:

- プロンプト変更・モデル変更・テンプレ変更が本番チャンネルに直接出る
- 失敗作の動画は非公開化しても **動画ID・履歴がチャンネルに残り、評価アルゴリズムに影響する可能性**
- 1日1〜2本の規模でも、変更の度にガチャを引くことは資産(動機 B + C)を毀損する

## 決定

- **dryrun モード**(`--dryrun` フラグまたは管理UI のトグル)を MVP 必須機能に追加
- dryrun モードの挙動:
  - 楽曲生成・連結・サムネ生成・動画合成・タイトル説明文生成までは **本番と同一の経路で実行**
  - **YouTube への upload のみスキップ**(代わりに「投稿予定メタデータ」と動画ファイルパスを記録)
  - ローカルで動画再生してレビュー可能
  - 管理UI から「dryrun の出力を承認 → 本番投稿」のフローも提供
- 重要な変更(プロンプトの大幅変更・モデル切替)時は **dryrun を 3〜7 サイクル走らせてから本番反映** を運用ルール化
- 改善計画の人間レビュー枠(ADR-0006)も dryrun と統合運用可能

## 結果

### 良い影響

- 変更のリスクを本番チャンネルに出さずに評価できる
- 反転コストが下がる(失敗作が公開されない)
- 開発・本番分離なしの運用と整合(同一マシン・同一コードベース)

### 悪い影響・トレードオフ

- 動画ファイルを毎回生成するため、dryrun 期間中もディスク消費は同じ
  - 緩和: dryrun の動画は短い retention(例: 48時間)で自動削除
- dryrun と本番の差分は「upload のみ」とシンプルに保つ必要(余計なフラグ分岐を避ける)

### 受容したリスク

- dryrun を「常時 ON」にすると永遠に投稿されない → 運用ルールで縛る

## 検討した代替案

- **別チャンネルでテスト:** 1人運用には負荷が高い。不採用(将来規模拡大時に検討)。
- **ステージング環境の構築:** 開発・本番分離なし方針と矛盾。不採用。
- **dryrun なし:** 反転コストが高すぎる。不採用。
