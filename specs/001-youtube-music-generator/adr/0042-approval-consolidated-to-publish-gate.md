# ADR-0042: 承認を公開ゲート 1 点 + 運営判断に集約する

- **ステータス:** Accepted
- **日付:** 2026-07-25
- **決定者:** @seita
- **タグ:** frontend / ops / policy

## 背景

旧設計では、1 本の動画を公開するまでに人の操作が次のように分散していた。

**純粋な承認 4 種**

| 承認 | 出典 |
|---|---|
| Daily Plan 承認(compile → validate → approve、強制承認あり) | ADR-0039 |
| dryrun 審査(pending → approved / rejected) | ADR-0007、ADR-0025 |
| Weekly Plan(改善計画)承認 | ADR-0006、ADR-0032 |
| トラック単位の人間レビュー(accepted / rejected / regenerating) | ADR-0039 |

**手動ゲート 6 系統**: scheduler 手動 enable(再起動のたび)、dryrun モード切替、feature gate `PLAN_APPROVAL_V2` の mode 切替、`make panic-stop` からの復帰、新ジャンル / 新テンプレの dryrun 経由必須、run-now の手動起動。

結果として **1 本の投稿に直列で 3 回**の人の介入が必要で、しかもそれぞれ意味が違う(仕様の妥当性 / 音の品質 / 公開可否)。ユーザーの評価は「承認パターンが多すぎてめんどくさい」であり、実際には形骸化したワンクリック承認になっていた。形骸化した承認は、Constitution III が意図した「人間が止められる状態」を実質的に提供しない。

## 決定

### (1) 人の判断は 2 種類だけにする

| 判断 | 頻度 | 対象 |
|---|---|---|
| **公開ゲート** | 枠ごと(L0 時) | その枠を公開するか / 却下するか |
| **運営判断** | 低頻度 | ジャンルの昇格 / 撤退 / 新規追加、自動運転レベルの変更 |

これ以外に人の承認を要求する工程を作らない。運営判断は監査ログに記録する。

### (2) 廃止する承認・ゲート

- Daily Plan の承認 / 強制承認 / 再生成承認(ADR-0039)。仕様確定(compile)と検証(validate)は**人の承認なしで自動実行**する内部処理として残す
- dryrun 審査(ADR-0007、ADR-0025)。dryrun という概念自体を廃止し、公開ゲートに一本化する
- Weekly Plan(改善計画)の承認。方針は自動反映とし、**ジャンルの形が変わる判断(昇格 / 撤退 / 新規追加)のみ**を運営判断として残す
- トラック単位の人間レビュー。自動検査は残す((3))が、人が全トラックを聴いて accept する工程は置かない
- scheduler の手動 enable。再起動後は自動再開する(停止は ADR-0044 の明示的な停止状態でのみ表現する)
- feature gate `PLAN_APPROVAL_V2`

### (3) 自動検査は残し、人の承認対象から外す

指紋照合(ADR-0005)、AI 開示フラグ(ADR-0020)、音量・尺・無音率などの自動品質検査(旧 `audio_qa_v1`)は検査工程として残す。ただし結果に対する扱いを次のように変える。

- **合格**: そのまま次工程へ。結果は枠詳細の検査サマリに表示する
- **指紋一致**: 該当トラックのみ自動再生成(ADR-0005 を継承)。3 回連続一致でジャンル一時停止 + 通知
- **品質不合格**: 該当トラックを自動再生成。リトライ上限を超えたら枠を `failed` にして通知(ADR-0045)

人が見るのは「公開してよいか」の 1 点であり、個々のトラックの合否判定ではない。

### (4) 公開ゲートの内容

L0(ADR-0043)では、パッケージング完了後に枠が `awaiting_approval` になり、枠詳細で次を確認して承認 / 却下する。

- プレビュー(動画・タイトル・説明文・チャプター)
- 検査サマリ(AI 開示・指紋・音量・形式検証)
- **承認**: `approved` へ。公開予定時刻に自動公開
- **却下**: 理由(自由記述)を添えて `rejected_pending` へ(ADR-0045)。**却下理由は次回の企画 LLM への入力になる**(旧 dryrun 却下理由の活用を継承)

## 結果

### 良い影響

- 1 本あたりの人の操作が 3 回から **1 回**(L0)または 0 回(L1 / L2)になる
- 「この承認は何を判断しているのか」が 1 つに定まり、形骸化しにくい
- Plan の状態機械(ADR-0039 の 10 状態)が枠の状態機械に吸収され、状態数が減る(ADR-0045)

### 悪い影響・トレードオフ

- 仕様確定前に人が介入する余地が無くなる。企画が的外れでも音楽生成の GPU 時間を消費してから気づく。**工程単位のやり直し(ADR-0046)でやり直せることを前提に受容する**
- トラック単位の人間レビューが無くなるため、自動検査を通過した「つまらない曲」は公開ゲートまで進む。公開ゲートでの却下 → 部分再生成で対応する

### 受容したリスク

- 自動検査の閾値が甘いと、人が気づかないまま品質の低い音源が公開ゲートに並ぶ。閾値は運用しながら version bump で更新する(旧 `audio_qa_v1` の方針を継承)

## 検討した代替案

- **承認を残したままワンクリック化する:** 旧設計の実態がすでにそれであり、介入ポイントの数は減らない。不採用
- **公開ゲートも廃止して全自動にする:** L2 として選択可能にする(ADR-0043)。ただし既定にはしない
- **トラックレビューだけ残す:** 6 トラック × 枠数の試聴は個人運用で続かない。自動検査 + 公開ゲートでのプレビュー試聴に統合
