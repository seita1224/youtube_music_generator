# ADR-0012: OAuth2 リフレッシュトークン = PostgreSQL に対称鍵暗号化で保存

- **ステータス:** Accepted
- **日付:** 2026-05-25
- **決定者:** @seita
- **タグ:** backend, security, infra

## 背景

YouTube への投稿には OAuth2 認証 + リフレッシュトークン管理が必要(../requirements.md §認証)。
リフレッシュトークンは事実上「本番チャンネルへの全権鍵」であり、扱いを誤ると以下のリスクが直結:

- 漏洩 → 他者による乗っ取り・なりすまし投稿(動機 B+C の資産同時喪失)
- バックアップから流出 → `pg_dump` の平文ダンプが意図せず外部に出る
- リポジトリ誤コミット → 公開リポジトリ・LLM プロンプトログ等に混入

DB を PostgreSQL に置く前提(ADR-0010)なので、トークン保管もそこに揃えると運用が一貫する。
ただし平文保存は受容できない。

## 決定

- リフレッシュトークン・アクセストークンは **PostgreSQL の専用テーブル**(例: `oauth_credentials`)に保存
- 値は **対称鍵暗号化**(Python `cryptography` の `Fernet` を使用)してから DB に格納
- 対称鍵(`OAUTH_FERNET_KEY`)は **環境変数** で渡す
  - `.env` ファイルで管理、`.env` は **`.gitignore` で除外**
  - リポジトリには `.env.example`(値抜き)のみコミット
- バックアップ運用:
  - `pg_dump` ダンプには暗号化済みのトークンが含まれる(ダンプ単体では復号不能)
  - 対称鍵 `.env` は別経路でバックアップ(別ディスク・別マシン)
  - **ダンプと鍵を同じ場所に置かない**
- 失効検知:
  - リフレッシュトークン失効による API 401/403 を捕捉し Slack 通知
  - 再認証フローは管理UI から手動実行可能
- 鍵ローテーション:
  - 必要時は新旧鍵を併用するマイグレーション関数で再暗号化
  - 通常運用では年1回程度の頻度を想定

## 結果

### 良い影響

- DB ダンプ単体が漏れても復号不能(鍵が別管理)
- 運用レイヤが Postgres に統一され、コードと運用が一貫する
- リポジトリ誤コミット時の被害が「暗号化済み値のみ」に限定される(`.env` を `.gitignore` 必須)

### 悪い影響・トレードオフ

- 対称鍵の管理運用が必要(`.env` バックアップ・配布・ローテーション)
  - 緩和: 1台運用なので配布リスクは限定的、年次ローテーションで十分
- アプリ起動時に `OAUTH_FERNET_KEY` 環境変数が必須 → 設定ミスで起動失敗
  - 緩和: 起動時バリデーションでエラーメッセージを明示

### 受容したリスク

- 対称鍵 `.env` を平文で持つので、マシン本体の compromise には弱い
  - 1台運用前提では受容、将来 OS Keyring / HSM への移行余地あり

## 検討した代替案

- **PostgreSQL に平文保存:** `pg_dump` 経由の漏洩リスクが大きすぎる。不採用。
- **OS Keyring(GNOME Keyring 等):** リモート運用(SSH 経由のセッション)では Keyring へのアクセスが煩雑、ヘッドレス環境との相性が悪い。不採用。
- **別ファイル(`~/.config/yt-music/credentials.json` + `chmod 600`):** Google 公式 quickstart 形式で標準的だが、DB と運用レイヤが分かれ、バックアップ運用が分岐する。不採用。
